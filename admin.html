SHARING RULE RESEARCH

Power rule on cumulative contribution

Each co-op shares by a power rule on members' cumulative contribution, α ≥ 1 (arXiv:2606.28217). This co-op uses α = 1 as an example.

Only revenue from contribution is shared.

Who executes payout is not decided. Recording and paying are separate transactions.

Review notes 7 open questions · 3 assumptions · sources

OPEN QUESTIONS

  1. Priority: the MVP covers normal-user screens only, so this operations screen is kept as a later-stage draft.
  2. Can every participant become an Admin? Who should see Admin in "Viewing as"?
  3. Sign-in: basic only, basic + social, or social only. How is an admin told apart (Join vs Sign in)?
  4. Who approves participation: the platform Admin alone (SFR-005 draft), or shared with the co-op leader?
  5. Who executes settlement payout, and how is the platform's share (fee) shown?
  6. Should version 1 include a limit on how much can be unlearned and a warning modal for the performance drop? Proposed, not agreed.
  7. The TL++ (neural network) path has no unlearning method yet. What should this queue show for a TL++ co-op request?
  8. System scale: a few organizations or millions of devices? Paging of these lists depends on it.

ASSUMPTIONS

  1. Admin screens are low priority for the MVP, and a terminal would also do. This page is for lo-fi review only and is built after the Participant screens.
  2. Admin is one FLARE project_admin, following the SFR-005 / SER-001 drafts. Approve buttons exist only on this page.
  3. All unlearning and retraining run buttons are disabled. The unlearning module connects in about three months.

MOCK NOTES

  1. The sample account (JK, Org A) is shown holding Admin so the "Viewing as" switch can be walked through. admin@travi.example in the log is a separate sample admin.
